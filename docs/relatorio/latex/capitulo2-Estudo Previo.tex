    \chapter{Estudo Prévio}

\section{Análise das APIs de Inferência}
    O estudo inicial comparou APIs de inferência compatíveis com os fornecedores OpenAI, Anthropic e Gemini, bem como execuções locais e compatíveis através de Ollama e de APIs que cumprem o padrão OpenAI, como Groq. Esta análise não teve apenas um papel descritivo, mas foi a base para identificar os conceitos que podiam ser normalizados no OmniAI SDK e os pontos onde a normalização teria de preservar extensões específicas de cada fornecedor. Para esse efeito, foram executados e documentados pedidos de geração simples, pedidos com \textit{streaming}, pedidos com \textit{tool calling}, respostas com contabilização de tokens e casos de configuração de geração. É de notar que o uso de vídeos, imagens e outros formatos suportados por estas APIs seria interessante, mas aumentaria demasiado o escopo do estudo.

    O estudo das APIs de inferência mostrou que estas partilham de diversos conceitos semelhantes, mas permitem a utilização dos mesmos de maneira diferente. A OpenAI organiza a interação em torno de \texttt{chat/completions}, com \texttt{messages}, \texttt{choices}, \texttt{tool\_calls} e eventos incrementais baseados em \texttt{delta} \cite{openai_api}. A Anthropic usa uma API de \texttt{messages}, onde o \texttt{system prompt} está no nível de topo, o campo \texttt{max\_tokens} é obrigatório, e o conteúdo da resposta é uma lista de blocos como \texttt{text}, \texttt{tool\_use} ou \texttt{thinking} \cite{anthropic_api}. A Gemini modela o pedido como \texttt{contents} compostos por \texttt{parts}, agrupa parâmetros em \texttt{generationConfig}, representa ferramentas por \texttt{functionDeclarations} e introduz conceitos próprios como \textit{thought signatures} e \texttt{thinkingConfig} \cite{google_gemini_api}. Na tabela seguinte, poderemos observar melhor essas diferenças.

    A análise dos campos de pedido revela que, embora os três fornecedores partilhem conceitos equivalentes, cada um organiza o corpo JSON de forma distinta. A OpenAI e a Anthropic colocam a maioria dos parâmetros como propriedades soltas na raiz do objeto, enquanto a Gemini agrupa-os dentro de \texttt{generationConfig}. A diferença mais notável está na identificação do modelo: OpenAI e Anthropic incluem-na no corpo do pedido, enquanto a Gemini a incorpora diretamente no URI da chamada HTTP, tornando o \textit{endpoint} dinâmico. O \textit{system prompt} também diverge consideravelmente: a OpenAI trata-o como uma mensagem com papel \texttt{system}, a Anthropic eleva-o a uma propriedade de topo, e a Gemini define-o através de um objeto \texttt{system\_instruction} separado. Estas diferenças tornam evidente que uma tradução superficial de nomes de campos seria insuficiente para construir uma abstração que cubra os três fornecedores.

    A comparação das respostas reforça a perceção de que as três APIs divergem significativamente na organização estrutural, apesar de exprimirem os mesmos conceitos. A OpenAI encapsula a resposta dentro de um \textit{array} \texttt{choices} que contém um objeto \texttt{message}, a Anthropic expõe o conteúdo diretamente na raiz através de um \textit{array} \texttt{content} com blocos tipados, e a Gemini utiliza \texttt{candidates} com \texttt{parts} e conceitos adicionais como \texttt{thoughtSignature}. Um aspeto particularmente relevante é a representação dos argumentos em chamadas de ferramenta: a OpenAI serializa-os como \textit{string} JSON dentro do campo \texttt{arguments}, obrigando a uma deserialização adicional, enquanto a Anthropic e a Gemini devolvem JSON nativo nos campos \texttt{input} e \texttt{args}, respetivamente. A contabilização de \textit{tokens} também difere na nomenclatura e granularidade: a Gemini, por exemplo, expõe um campo adicional \texttt{thoughtsTokenCount} que permite distinguir os tokens de raciocínio dos tokens de conteúdo efetivo.

\subsection{Conclusão do Estudo das APIs de Inferência}

    A realização deste estudo envolveu dificuldades práticas que merecem ser documentadas. Para a API da OpenAI, o acesso direto à API oficial implica custos de utilização, pelo que os testes foram realizados utilizando a API da Groq \cite{groq_api}, que oferece um plano gratuito e implementa uma interface compatível com o formato da OpenAI (\texttt{/v1/chat/completions}). Adicionalmente, foram executados testes complementares contra uma instância local de Ollama \cite{ollama_docs}, que também expõe um \textit{endpoint} compatível com o formato OpenAI. Para a API da Anthropic, a situação foi semelhante: a API oficial requer um plano de subscrição pago, pelo que os testes foram realizados utilizando o Ollama, que disponibiliza um \textit{endpoint} compatível com o formato da Anthropic (\texttt{/v1/messages}). Embora o Ollama implemente corretamente as interfaces de compatibilidade para pedidos simples, de \textit{streaming} e com parâmetros de configuração, algumas funcionalidades mais avançadas — nomeadamente o \textit{tool calling} estruturado e a geração de blocos de raciocínio (\textit{thinking}) — apresentaram limitações quando executadas em modelos de pequena dimensão como o \texttt{llama3.2:1b}. Nesses casos, os exemplos de resposta foram ajustados para refletir com fidelidade o comportamento documentado das APIs oficiais. O Gemini foi o único fornecedor cujos testes foram executados diretamente contra a API oficial, uma vez que esta disponibiliza um nível de acesso gratuito.

    Do ponto de vista técnico, o estudo permitiu concluir que as três APIs partilham um conjunto de conceitos fundamentais — mensagens, papéis, ferramentas, \textit{streaming} e contabilização de \textit{tokens} — mas implementam-nos de formas estruturalmente diferentes. As diferenças manifestam-se na nomenclatura dos campos, na organização hierárquica do JSON, na localização dos parâmetros de configuração e nos mecanismos de ativação de funcionalidades como \textit{streaming} e raciocínio. Esta análise permitiu perceber que uma abstração que pretenda cobrir estes três fornecedores precisa de ir além de uma simples tradução de nomes, exigindo uma compreensão das diferenças semânticas e estruturais observadas nos pedidos e respostas reais.

    O caso de \textit{tool calling} foi especialmente relevante, porque é onde as APIs mais divergem apesar de exprimirem uma intenção semelhante: permitir que o modelo peça a execução de uma função externa. Na OpenAI, a ferramenta é descrita em \texttt{tools[]} e a resposta devolve \texttt{tool\_calls} com argumentos serializados como JSON em string. Na Anthropic, a ferramenta é descrita com \texttt{name}, \texttt{description} e \texttt{input\_schema}; a resposta inclui blocos \texttt{tool\_use}, e o resultado da execução regressa ao modelo como bloco \texttt{tool\_result}. Na Gemini, as ferramentas são \texttt{functionDeclarations}, a chamada surge em \texttt{functionCall}, e o resultado é enviado como \texttt{functionResponse}.

    \section{Model Context Protocol (MCP)}
    O \textit{Model Context Protocol} define uma arquitetura cliente-servidor para disponibilizar contexto a aplicações baseadas em modelos. Na terminologia do protocolo, um \textit{host} é a aplicação de IA que inicia e coordena ligações, os \textit{clients} mantêm ligações 1:1 com servidores, e os \textit{servers} expõem capacidades como ferramentas, recursos e \textit{prompts} através de mensagens JSON-RPC e transportes normalizados \cite{mcp_protocol,mcp_architecture}. Esta separação é relevante porque transforma integrações externas em unidades descobertas e invocadas através de um protocolo comum, em vez de as embutir diretamente na API de inferência de cada fornecedor.

    O estudo do MCP foi realizado em paralelo com a análise das APIs de inferência, mas com um objetivo diferente. Enquanto a análise das APIs procurou compreender pedidos e respostas de modelos, o estudo do MCP procurou compreender como ferramentas externas podem ser descritas, listadas e executadas de forma independente do fornecedor de LLM. Os conceitos centrais observados foram:

    \begin{itemize}
        \item \textbf{Tools}: funções ou ações executáveis por um servidor MCP, descritas por nome, descrição e esquema de entrada.
        \item \textbf{Resources}: dados ou documentos que podem ser descobertos e lidos por clientes MCP, normalmente identificados por URIs estáveis.
        \item \textbf{Prompts}: modelos reutilizáveis de interação, que podem encapsular instruções, argumentos e mensagens estruturadas.
        \item \textbf{Transports}: mecanismos de comunicação como \texttt{stdio}, SSE, HTTP com \textit{streaming} e WebSocket, dependendo do ambiente de execução.
    \end{itemize}

    Para ganhar contexto prático, foi criado um projeto experimental de pequena dimensão, usado como ``projeto brinquedo'', onde foram implementados servidores MCP e clientes MCP com a biblioteca Kotlin MCP. Esse protótipo permitiu validar o ciclo básico de criação de um servidor, registo de capacidades, ligação a partir de um cliente e troca de mensagens. A utilização da biblioteca oficial \texttt{io.modelcontextprotocol:kotlin-sdk} também mostrou que a abordagem é compatível com Kotlin Multiplatform e que existem APIs próprias para construir clientes, servidores, ferramentas, recursos, \textit{prompts} e transportes \cite{mcp_kotlin_sdk}.

    Esta análise ajudou a distinguir dois problemas que, à primeira vista, podiam parecer iguais. O primeiro problema é a normalização de contratos de inferência, resolvido no SDK através de \textit{contracts}, \textit{translators}, \textit{inbounds}, \textit{outbounds} e domínio comum. O segundo problema é a gestão de ferramentas externas, onde o MCP oferece uma forma padronizada de descrever e executar capacidades. No final deste estudo, tornou-se natural desenhar um módulo de MCP Broker: não como ponto de partida do Capítulo 2, mas como consequência da necessidade de intermediar ferramentas externas sem acoplar cada adapter de inferência a cada ferramenta disponível.

\chapter{MCP Broker e Ferramentas Externas}

O \textbf{MCP Broker} surge como uma extensão natural da \textbf{Gateway}: deixar de a tratar apenas como um ponto de entrada para inferência e aproximá-la de uma \textit{gateway} de IA mais completa. Em muitos cenários, um modelo só consegue produzir uma resposta útil se puder consultar recursos externos, chamar ferramentas ou executar ações controladas. É nesse espaço que entra o \textbf{Model Context Protocol (MCP)}.

O que foi concretamente implementado neste módulo é uma \textbf{MCP Gateway} funcional: um servidor MCP autónomo que lê ficheiros de configuração \textbf{YAML} de forma declarativa, regista automaticamente as ferramentas neles descritas, e expõe-as a qualquer cliente MCP compatível, como o \textbf{MCP Inspector}. Adicionalmente, o \textbf{MCP Broker} é capaz de se ligar a outros servidores MCP externos e de expor as suas ferramentas como proxies locais, funcionando como um ponto de agregação centralizado. Com isto, a Gateway deixa de ser apenas um \textit{proxy} de inferência e passa a ser uma infraestrutura de IA mais completa.

A implementação assenta em duas bibliotecas principais: \texttt{io.modelcontextprotocol:kotlin-sdk} (versão 0.13.0) \cite{mcp_kotlin_sdk}, que fornece o servidor MCP, os tipos do protocolo e os transportes suportados (\textit{stdio}, SSE, Streamable HTTP, WebSocket); e \texttt{net.mamoe.yamlkt} (versão 0.13.0) \cite{yamlkt_ref}, que é responsável por desserializar os ficheiros YAML de configuração em objetos Kotlin de forma declarativa. O cliente HTTP utilizado para comunicar com as APIs externas é o \textbf{Ktor} \cite{ktor_ref}.

\section{Modelos de Domínio e DTOs}

O MCP Broker organiza a sua configuração em duas camadas distintas: os \textbf{DTOs} (Data Transfer Objects), que representam a estrutura dos ficheiros YAML, e os \textbf{modelos de domínio}, que são os objetos internos sobre os quais a lógica do MCP Broker efetivamente opera. Esta separação evita que o código fique dependente do formato de serialização.

\subsection{DTOs de Configuração}

Os DTOs representam diretamente a estrutura dos ficheiros YAML e são anotados com \texttt{@Serializable}, a anotação da biblioteca \texttt{kotlinx.serialization}, para que o \texttt{yamlkt} os consiga desserializar automaticamente. O \texttt{BrokerConfigDto} é o objeto de entrada, agregando as três listas de configuração possíveis.

A diferença mais relevante entre os DTOs e os modelos de domínio está na representação dos schemas de entrada. No DTO, estes campos são deserializados como \texttt{YamlMap}, preservando a estrutura em árvore do YAML. No modelo de domínio, essa estrutura é convertida para \texttt{JsonObject}, o tipo nativo da biblioteca \texttt{kotlinx.serialization}, garantindo que os tipos de cada valor (inteiro, booleano, objeto aninhado, etc.) são preservados corretamente.


\section{Configuração Declarativa em YAML}

Toda a configuração do MCP Broker é feita através de ficheiros \textbf{YAML} colocados numa pasta de configuração. Cada ficheiro pode declarar três secções independentes:

\begin{itemize}
    \item \textbf{\texttt{tools}}: ferramentas REST que o MCP Broker expõe nativamente.
    \item \textbf{\texttt{contexts}}: conteúdo estático exposto na forma de recursos.
    \item \textbf{\texttt{mcpServers}}: servidores MCP externos aos quais o MCP Broker se liga.
\end{itemize}

\subsection{Descrição de Ferramentas REST}

A configuração de uma ferramenta REST é feita de forma declarativa, sem escrever código. Basta indicar o nome, a descrição, o URL de destino, o método HTTP, os cabeçalhos, e as secções de entrada de dados. Para permitir um roteamento preciso dos argumentos, a validação de entrada divide-se em três partes:

\begin{itemize}
    \item \textbf{\texttt{pathSchema}}: parâmetros que são substituídos diretamente no URL, através da sintaxe de chavetas no formato \texttt{\{chave\}}.
    \item \textbf{\texttt{querySchema}}: parâmetros que são acrescentados ao URL como variáveis de interrogação.
    \item \textbf{\texttt{bodySchema}}: parâmetros que são enviados no corpo do pedido HTTP como JSON, suportando tipos complexos como objetos aninhados, arrays, números e booleanos.
\end{itemize}

O exemplo seguinte ilustra uma ferramenta que utiliza simultaneamente os três tipos referidos:

\begin{lstlisting}[caption={Exemplo de ferramenta REST configurada via YAML.}]
tools:
  - name: "test_url_vs_body"
    description: "Ferramenta de teste com path, query e body."
    targetUrl: "https://postman-echo.com/post?id={test_id}"
    method: "POST"
    headers:
      Accept: "application/json"
    pathSchema:
      test_id: "string"
    querySchema:
      filtro: "string"
    bodySchema:
      mensagem: "string"
      idade: "number"
      opcoes:
        type: "object"
        properties:
          notificar:
            type: "boolean"
\end{lstlisting}

\subsection{Contextos Estáticos como Recursos}

Para além das ferramentas REST, o MCP Broker permite declarar \textbf{contextos estáticos} que são expostos como recursos MCP. Um contexto é um bloco de texto associado a um URI fixo, que os clientes MCP podem ler diretamente. É útil para partilhar, por exemplo, documentação de APIs ou instruções de sistema que o modelo deve ter em conta.

\begin{lstlisting}[caption={Exemplo de contexto estático exposto como recurso MCP.}]
contexts:
  - name: "github-api-schema"
    uri: "context://github-api-schema"
    description: "Esquema da API GitHub para auxiliar o modelo."
    mimeType: "text/plain"
    content: |
      A API GitHub usa autenticacao via token Bearer.
      Endpoints relevantes: GET /repos/{owner}/{repo}
\end{lstlisting}

\subsection{Proxy de Servidores MCP Externos}

O MCP Broker pode também ligar-se a outros servidores MCP no papel de cliente e expor as ferramentas desses servidores como se fossem locais. Esta funcionalidade de \textit{proxy} é parametrizada na secção \texttt{mcpServers}, onde se indica o nome, o tipo de transporte e os parâmetros de inicialização:

\begin{lstlisting}[caption={Exemplo de configuração de proxy para um servidor MCP externo.}]
mcpServers:
  - name: "filesystem-mcp"
    transport: STDIO
    command: "npx"
    args:
      - "-y"
      - "@modelcontextprotocol/server-filesystem"
      - "/workspace"
\end{lstlisting}

Quando o MCP Broker arranca, liga-se a cada servidor externo configurado e descobre as suas ferramentas. Essas ferramentas são então registadas localmente com o prefixo do nome do servidor (por exemplo, \texttt{filesystem-mcp\_read\_file}), ficando disponíveis para qualquer cliente MCP ligado ao MCP Broker como se fossem ferramentas locais.


\section{Arranque e Inicialização do MCP Broker}

Quando o Broker arranca, percorre uma sequência de passos bem definida antes de estar pronto a receber ligações:

\begin{enumerate}
    \item \textbf{Leitura do YAML}: O \texttt{YamlConfigParser} lê todos os ficheiros presentes na pasta de configuração e desserializa cada um num \texttt{BrokerConfigDto}, usando a biblioteca \texttt{yamlkt}. Os schemas de entrada ficam nesta fase representados como \texttt{YamlMap}.

    \item \textbf{Mapeamento para o Domínio}: O \texttt{ConfigMapper} converte cada DTO no modelo de domínio correspondente. Os \texttt{YamlMap} dos schemas são transformados recursivamente em \texttt{JsonObject}, preservando os tipos nativos de cada valor.

    \item \textbf{Registo de Ferramentas REST}: O \texttt{ToolRegistrar} percorre a lista de \texttt{RestToolDefinition} e regista cada ferramenta no servidor MCP, usando o Kotlin MCP SDK. Para cada uma, gera automaticamente um JSON Schema unificado a partir dos três schemas parciais (\texttt{pathSchema}, \texttt{querySchema} e \texttt{bodySchema}), que é o que o cliente recebe ao fazer \texttt{tools/list}.

    \item \textbf{Registo de Contextos}: O \texttt{ContextRegistrar} publica cada \texttt{ContextDefinition} como um recurso MCP, usando igualmente o Kotlin MCP SDK. Cada recurso fica acessível pelo URI declarado no YAML.

    \item \textbf{Ligação a Servidores Externos}: O \texttt{McpClientManager} estabelece ligação a cada servidor MCP externo configurado. O \texttt{ProxyToolRegistrar} descobre as ferramentas disponíveis em cada um e regista-as localmente, de forma a que o MCP Broker possa encaminhar as chamadas.

    \item \textbf{Arranque do Servidor}: Por fim, o \texttt{BrokerServer} inicia os transportes configurados (Stdio, SSE, Streamable HTTP ou WebSocket) e fica a aguardar ligações de clientes MCP.
\end{enumerate}


\section{Hot-Reload de Configuração}

O MCP Broker suporta \textbf{hot-reload} dos ficheiros YAML em tempo de execução, sem necessidade de reiniciar. Existe uma rotina dedicada que monitoriza de forma contínua o diretório de configuração. Sempre que uma modificação é detetada pelo sistema operativo, despoleta-se um novo ciclo de recarga. O serviço reconstrói a árvore de dependências, aplica o mapeamento e atualiza a representação exposta no servidor, procedendo de maneira transparente para quem já se encontre ligado.


\section{DSL de Configuração}

O MCP Broker expõe uma \textbf{DSL Kotlin} para ser instanciado programaticamente, através da função \texttt{mcpBroker\{\}}. Esta abordagem é útil quando o MCP Broker é integrado numa aplicação maior, como um servidor Ktor já existente:

\vspace{0.5em}
\begin{lstlisting}[caption={Exemplo de configuração do MCP Broker via DSL Kotlin.}, language=Kotlin]
val broker = mcpBroker {
    info(name = "omni-mcp-broker", version = "1.0.0")

    configDirectory("./mcp-configs")

    httpClient(
        HttpClient(CIO) {
            install(ContentNegotiation) { json() }
        }
    )

    clientTransportFactory(McpClientTransportFactory())

    serverTransport(
        ServerTransportConfig.Stdio(
            input  = SystemFileSystem.source(Path("/dev/stdin")),
            output = SystemFileSystem.sink(Path("/dev/stdout")),
        )
    )
}

broker.start()
\end{lstlisting}
\vspace{0.5em}


\section{Fluxo de Execução}

Depois de inicializado, o Broker comporta-se como qualquer servidor MCP: os clientes comunicam com ele usando o protocolo MCP padrão. Quando um cliente realiza o pedido \texttt{tools/list}, recebe a lista completa de ferramentas disponíveis, incluindo tanto as ferramentas REST locais como as que foram descobertas nos servidores externos. Quando invoca uma ferramenta com \texttt{tools/call}, o Broker sabe exatamente o que fazer com base no registo feito no arranque:

\begin{itemize}
    \item Se for uma ferramenta REST, o \texttt{RestToolExecutor} constrói e executa o pedido HTTP correspondente usando o \texttt{HttpClient}, a interface genérica de cliente HTTP injetada no Broker. Os argumentos são distribuídos pelo URL (path e query) e pelo corpo do pedido, conforme o declarado nos schemas.
    \item Se for uma ferramenta em proxy, o Broker reencaminha a chamada para o servidor MCP externo e devolve a resposta tal como a recebeu.
    \item Se for um contexto, o cliente pode lê-lo diretamente via \texttt{resources/read}, recebendo o conteúdo estático associado ao URI.
\end{itemize}
